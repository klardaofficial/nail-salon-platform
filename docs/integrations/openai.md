# OpenAI integration

`OPENAI_CHAT_MODEL` and `OPENAI_IMAGE_MODEL` pin deployment-selected models; defaults are `gpt-5-mini` and `gpt-image-1`. Confirm model availability and cost in the target OpenAI project before release. Code uses the installed official JavaScript SDK.

Natural chat uses the Responses API with `store: false`, a stable safety identifier, serial tool calls, and app-owned context replay. The developer instructions in `features/conversation/respond.ts` define adaptive language, flexible booking policy, date/time basis, verified-role assistance, permissions, and response style. They include a bounded active catalog and draft, not arbitrary database content.

Every function definition uses strict JSON Schema with all properties required and nullable values where optional. The model may request a tool; `executeConversationTool` parses again with Zod, resolves the verified actor, rechecks entity scope, records `(conversation_id, tool_call_id)`, and returns the saved result on replay. Database idempotency adds a second boundary for booking and preview actions.

Implemented tools:

- Customer: save draft, create booking, list own bookings, cancel own booking, update own future booking, request style preview.
- Owner: paginated business booking records, complete database booking summaries, update its salon, manage its services, manage its technicians.
- Technician: paginated upcoming assigned bookings, complete assigned-booking summaries, submit own optional time off.

Image previews call `images.edit` with the WhatsApp source image, a constrained preservation prompt, high input fidelity, low-quality JPEG output, and up to the configured count. Base64 returned by OpenAI is decoded in memory and immediately uploaded. It never enters job results, SQL, logs, files, or documentation. `store: false` controls Responses storage; OpenAI and WhatsApp still apply their own data retention policies.

## Structured conversational replies

The Responses call uses the installed SDK's `zodTextFormat` via `text.format`. Final output is validated by `naturalReplySchema`: any canonicalizable language tag, text (up to 1024 characters), AI-written unavailableText, buttonLabel (20), sectionTitle (24), and up to ten unique options with id (200), title (20) and nullable description (72). The app selects WhatsApp buttons or lists by option count and preserves the AI's visible labels. Invalid output cannot enter the outbox as raw JSON. Each new greeting is interpreted by AI; there is no configured greeting shortcut.

The model must use current database tools for staff booking questions and summaries, describe only verified capabilities, and avoid computing totals from partial lists. `BOT_LOCALE` is the initial reference; customer/staff language overrides it and is retained per conversation. Supporting captions and ordinary notifications use separate recorded chat calls in the recipient's language. An AI outage uses the prior generated localized fallback, or neutral symbols before one exists; a completed booking/cancellation retains a neutral success receipt if the final model call fails.

The configured `platform_settings.platform_timezone` controls all date/time interpretation, relative dates, staff date boundaries and time off. The model must ignore personal/stated timezones, location, phone country, language and salon timezone for time interpretation. It must never ask for a timezone or disclose the configured timezone. Shared main-reply/localization instructions require visible dates and clock times without timezone names, abbreviations, offsets or explanatory qualifiers. Offset timestamps remain required for internal tool arguments. Supporting notifications receive already-formatted appointment times and must not convert them for the recipient.

The official hosted structured-output documentation was unreachable in this environment; the installed OpenAI SDK's `helpers/zod` and Responses types were checked and the generated strict schema is covered by application tests. Live language/style quality still requires synthetic provider evaluation.

All four read tools use the service-role Supabase API after verified edge identity, with no browser/admin-auth shortcut. They do not mutate bookings. Tool execution bookkeeping records and replays the result for the same conversation/call ID; a new call queries current data. The model never supplies contact ID, business ID, SQL, or authorization scope. RLS and service-only RPC grants remain defense in depth.

`save_booking_details` accepts nullable salonId and startsAt with offset, services, nullable technicianRef and additionalRequest. It writes only the verified actor's collecting draft, selecting its timezone from current platform settings; the model cannot supply a timezone argument. Invalid arguments or settings/write failures return tool errors. Replays reuse the recorded conversation/call result; a new call updates the same conversation draft.

`create_booking` accepts nullable salonId, a future startsAt with offset, services (including custom name snapshots), nullable technicianRef and additionalRequest. It resolves the active singleton business and current salon configuration and rejects stale explicit salon choices. Service IDs are matched only when an active global service or a service scoped to the selected salon is found; all other customer-supplied names remain as custom snapshots. It snapshots the platform timezone and names, creates one auto-confirmed booking, completes the draft and queues an assigned-technician notification. The database rechecks platform timezone even with a selected salon. Replayed tool calls and SQL idempotency keys return the original booking. Missing optional fields do not fail. Invalid time or inactive business/salon asks for a correction; a concurrently changed platform timezone requires refreshing settings and retrying internally without asking the person for a timezone.

`update_booking` accepts an identified booking UUID, desired nullable salon/technician IDs, services, additional request, and a future `startsAt` timestamp with offset. The assistant first lists the customer's bookings when the target is not clear, preserving each unmentioned value in the complete update arguments. The database locks and verifies that it is the customer's confirmed future booking, validates the active salon and current platform timezone, updates that row's appointment time, salon, service snapshots, technician snapshot, and request, and appends one idempotent `booking.rescheduled` event with prior/new scheduling values. It does not cancel, recreate, or change the immutable booking reference. A technician reassignment queues a cancellation notification for the prior assigned technician and a confirmation notification with the updated details for the newly assigned technician; update-call keys deduplicate each delivery across retries. Foreign, cancelled, started, inactive-salon, invalid-time, or stale-timezone requests return a safe error. The conversation-call key prevents duplicate event records on replay.

`owner_manage_service` accepts `action`, nullable `salonIds`, nullable `serviceId`, `name`, and `description`. `salonIds=null` creates or updates a global service; one or more IDs create or replace its salon restrictions. The verified owner must still own every supplied salon, and the tool replaces scope rows idempotently on a replayed call. It rejects missing services, unknown salons, revoked ownership, and database failures without creating partial booking data.

Customer, owner and technician booking lists format `starts_at` in the current platform timezone for their `local_time_label`, without timezone suffixes. Cancellation notification parameters do the same. Historical booking instants/snapshots remain unchanged; old labels containing timezone text are not reused in these conversation paths. For example, a stored `08:00Z` appointment displays `15:00` when the platform setting is `Asia/Bangkok`, regardless of the salon or person's timezone.

Staff summary `dateBasis=created` uses the same booking-created/status/customer definitions as dashboard reporting; `appointment` instead filters starts_at and is explicitly identified in the response. For example, a booking created on 16 September for 19 September counts in a 16 September created-date summary and a 19 September appointment-date summary. Dashboard charts/API/CSV definitions remain unchanged.
