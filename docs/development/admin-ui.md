# Admin UI conventions

The dashboard uses an English client-only root with Ant Design runtime styles. `AdminProviders` sets `en_US`, shared tokens, feedback context, and SWR defaults. Use Ant Design layout, menu, forms, drawers/modals, tables, tags, statistics, skeletons, and alerts before custom controls.

Layout, spacing, color, and typography on elements the project controls are Tailwind utility classes, generated from the shared `@theme` tokens in `src/app/theme.css` (admin-specific greys are namespaced as `--color-admin-*` and kept separate from the marketing palette). Admin's Tailwind entry (`src/app/admin/admin.css`) deliberately omits Preflight — `antd/dist/reset.css` is the reset here, and Preflight would add properties antd's reset never sets (notably `img, svg { display: block }`), silently shifting antd `Avatar`s and icons. Both `antd/dist/reset.css` and antd's runtime CSS-in-JS are unlayered, so they beat every Tailwind utility (including `!important` ones) on any property antd itself sets. Never write a utility that targets an antd-internal selector (`.ant-*`); the handful of cases that must reach into antd internals — the `.admin-sider` sticky/background `!important` fight, `.admin-stat-card .ant-statistic-content`, `.admin-org-card .ant-card-head`, `.admin-thread-list`'s skeleton/empty padding, `.admin-chat-choice`'s `!important` fight with a `Button` — stay as plain CSS in `admin.css`. `Select`/`DatePicker`/`TimePicker` root width/minWidth stay as inline `style` props rather than Tailwind classes, since antd's runtime may depend on those measured values for popup alignment; other antd form control roots (e.g. `InputNumber`) have no such constraint and take Tailwind classes normally. `ConfigProvider`'s theme tokens (in `admin-providers.tsx`) are the separate source of truth for antd's own internal rendering and are not derived from `@theme` — the two currently agree by construction, not by a shared definition. See the [Tailwind migration plan](tailwind-migration.md) for the full rationale and the marketing-side equivalent.

The admin UI renders only after browser hydration. Admin layouts, pages, and components never query Supabase or perform server-side data loading. All identity and operational reads use guarded `/api/admin/*` handlers through `useSWR(tupleKey, apiGet)`: the stable array key from `lib/api/keys.ts` includes every value that changes the request, and the explicit Axios fetcher is always the second argument. Mutations use `useSWRMutation` with tuple keys and `apiMutation`; reads and mutations of the same resource share a key so SWR revalidates it, and other affected keys are invalidated explicitly. Admin API reads bypass HTTP caching. `AdminShell` reads live identity and organization/navigation state through SWR so settings changes update navigation without a route refresh. Each screen provides loading, error, and empty behavior. Supabase clients belong behind API and feature boundaries only.

The root Overview is the organization directory. Once an organization is selected, Overview stays on that organization's scoped dashboard, including booking reporting and platform activity; there is no separate Analytics page. The root-only System accounts and System settings entries are hidden. Organization lifecycle actions are available from each card's overflow menu and retain a confirmation step.

Salon, service, and technician pages share `ResourceManager`; add fields/columns through `features/admin/resources.ts` and enforce the same schema in `resource-api.ts`. Organization Settings and the root System settings page both use `SettingsSection`: each Card is its own `Form` with its own `Save` button, so saving one section never resubmits an unrelated in-progress edit in another. Root System settings has a "WhatsApp (Meta)" section (credentials, template defaults, callback URL) and an "OpenAI" section (key, chat model, image model, and a structured per-model pricing row editor); these are the defaults every organization inherits until it configures its own.

Organization Settings separates organization identity/defaults, WhatsApp account identifiers, WhatsApp credentials, Simulator, and OpenAI into distinct sections. The WhatsApp Account section always shows the organization-owned WABA and receiving-phone IDs together with provider readiness and validation. The WhatsApp Credentials and OpenAI sections hide their override fields behind a configuration switch that opens automatically when a saved organization-specific override exists; while the switch is on, every field in that override is required, so the browser rejects an incomplete bundle before the API does. Saving with the switch off, or pressing the section's "Clear override & use root" button (shown only when an override is saved), clears the complete override so the root configuration applies — an organization can never keep only part of an override, and can never pair its own OpenAI model choice with the root's billing key. The WhatsApp Credentials section shows the webhook URL below the templates, identifying whether effective credentials come from root or the organization, and also owns click-to-chat details. The OpenAI section's off-state copy names the effective (root or organization) chat/image models actually in use. Validated active mappings accept real traffic automatically. There are no legacy top-level resource pages or unscoped admin API shims. Authentication forms submit to route handlers. The migration-created account has `must_change_password`; the shell disables other navigation and routes it to Account settings until the authenticated password change clears the flag.

Time fields use Day.js values inside Ant Design forms. Convert both create defaults and saved API values with the explicitly registered `customParseFormat` plugin, and serialize submitted times as `HH:mm`. Opening a create form after editing restores the resource defaults.

Use current component APIs: `Alert.title`, `Select.showSearch.optionFilterProp`, and Phosphor exports ending in `Icon`. Type-aware ESLint rejects APIs marked `@deprecated` by their declarations.

Overview adds platform activity below booking reporting, using the same calendar dates plus an independent source selector. It includes accessible tables, matching CSV export, and a paginated AI request log. The separate WhatsApp inbox uses responsive list/detail panes and the same `ChatMessageBubble` as the Simulator, with no reply callback or composer. See [observability](../architecture/platform-observability.md).

Analytics use Ant Design Charts. Charts must have a textual/table equivalent, filters shared with the API/CSV definition where applicable, and visible loading/error/empty states. The dashboard has no business filter because each deployment has one configured business. Keep the English dashboard separate from bot i18n and German marketing styles.
