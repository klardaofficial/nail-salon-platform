# Conversation state

One `conversations` row exists per WhatsApp contact/channel. Bounded text history lives in `conversation_messages`; media fields store IDs only. A single `booking_drafts` row collects salon, interpreted timestamp, service snapshots, soft technician reference, and optional request. Only collecting drafts enter the prompt; completed drafts do not prefill a new booking.

Real chats use `whatsapp`; the admin simulator uses `whatsapp_simulator`. The same contact has separate history, drafts, language preferences and tool executions in each. Business/booking data and role mappings are shared. Only authenticated simulator ingress attaches the trusted simulated-event marker. Source transport follows replies and technician notifications into durable outbox payloads; delivery never guesses it from the current environment flag.

The processor builds context from the latest 18 messages, active catalog, collecting draft, verified owner/technician mappings, platform timezone/defaults, current UTC time, and recent media ID. Service catalog entries with no `service_salons` rows are global; scoped entries appear only for their selected salon, while a No-preference location sees global entries only. The assistant asks about optional service choices only after that location decision and still retains any free-text service as a custom snapshot. It calls OpenAI with `store: false`, strict function schemas, serial tool calls, and structured final output. Text remains original; interactive titles and IDs are replayed together with message type and prior options.

`platform_settings.platform_timezone` is the sole conversation date/time authority for every salon and role. Salon timezones are omitted from AI catalog context, and collecting draft timezone context is refreshed from platform settings. Draft tools save the timezone from server settings rather than accepting an AI-supplied timezone. The prompt uses this setting for relative dates, clock times, staff date boundaries and time off, without inferring or asking for the person's timezone. Tool timestamps retain offsets internally; visible replies, controls, notification parameters and fallback receipts omit timezone names, abbreviations, offsets and explanations. Booking list tools and cancellation notifications format stored appointment instants in the current platform timezone instead of reusing historical labels. Booking instants and historical snapshots are not rewritten.

`BOT_LOCALE` is a default reference, not a restriction. The model chooses any valid language tag from customer text/history and generates every visible message and control label. The conversation stores `reply_locale` and `reply_unavailable_text`. Ambiguous numbers, dates, names, images, and taps preserve language. No first-message greeting bypass exists: a greeting or specific opening request produces one contextual reply through the same AI path. Historical `greeted_at` values are no longer used.

The final response contains locale, text, unavailableText, buttonLabel, sectionTitle, and up to ten options with stable IDs, AI-written titles, and optional descriptions. The app validates language syntax, nonempty/unique choices and WhatsApp size limits, then queues one text, button (1–3 options), or list (4–10 options) message. Typed answers remain equally supported. No model-generated control grants authorization or directly mutates booking data.

Verified owners start with owner capabilities; technicians start with assigned-booking/time-off capabilities. The AI explains appropriate actions in their language and offers corresponding controls. Staff enter personal customer flows only on request. Owner lists recheck business membership and paginate; technician tools re-resolve the active stored WhatsApp mapping on each invocation.

Inngest concurrency serializes events by WA ID. Provider IDs are unique in history, inbox events are unique, tool calls are unique by conversation/call ID, and booking inserts/updates use a conversation/call idempotency key. `update_booking` changes only an identified, customer-owned confirmed future booking while retaining its immutable reference; it can update time, salon, services, technician, and additional request, and its event records prior/new scheduling values. A technician reassignment queues deduplicated cancelled/confirmed notifications for the former/new technician respectively. The single contextual reply uses an event-specific outbox key. Provider failures use the latest AI-written unavailable text, or a language-neutral status when none exists. If booking/cancellation/update already succeeded but the final model reply fails, a neutral receipt retains the successful booking reference.

Saving inbound history does not mark the event complete. A retry with existing history resumes reply generation when no event-specific reply exists; if a reply is already queued, it reuses that payload and retries dispatch without calling AI again. Completion writes must succeed before the processor reports success. Salon context reads `salons.booking_interval_minutes`; the platform-level fallback is `platform_settings.default_booking_interval_minutes`.

The app never persists image bytes. Supporting notification/caption generation uses numeric AI usage instrumentation; localization failures use neutral status plus original details. Failed dispatch/delivery follows the existing durable recovery paths. See [ADR 0010](../adr/0010-web-whatsapp-simulator.md).
